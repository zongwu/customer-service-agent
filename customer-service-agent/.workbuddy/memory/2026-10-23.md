## 类型注解现代化（IDE 黄线告警修复）

用户发来 IDE 截图，`rag/bm25_retriever.py` 中 `Optional`、`List`、`-> None` 下方有黄色波浪线。

### 根因判定（不靠猜）

截图黄线标在 `Optional` / `List` 上，而第 12 行**已导入** `from typing import List, Optional`
——所以不可能是"未解析"，只能是**类型检查器把 typing 的旧式别名标记为 deprecated**。

写 AST 脚本全量排查，发现 5 个文件使用废弃别名：
- `bm25_retriever.py`: List, Optional
- `fusion.py`: Dict, List, Optional（且 `Iterable` 未使用）
- `loader.py`: List
- `reranker.py`: List, Tuple, Optional
- `retriever.py`: List, Optional
- `vectorstore.py`: List, Optional

### 改造

PEP 585/604 新式语法（项目 Python 3.13，完全支持）：
- `List[X]` → `list[X]`
- `Dict[K,V]` → `dict[K,V]`
- `Tuple[...]` → `tuple[...]`
- `Optional[X]` → `X | None`
- 前向引用：`Optional["BM25Index"]` → `"BM25Index | None"`

保留 `Iterable`/`Callable`/`TypeVar`/`Any`/`Sequence`——这些 typing 成员**未被 PEP 585 废弃**，
换成内置泛型反而不对（`Sequence` 无内置等价物）。

同时：
- `agent/`、`api/` 7 个占位文件补 `from __future__ import annotations`
  （接 DeepSeek 时必然要用 `X | None` 语法，提前铺好）
- 新增 `pyrightconfig.json`：pythonVersion 3.13、typeCheckingMode basic、
  明确 `reportDeprecated: warning` 与 `reportMissingTypeStubs: none`

### 关键验证点

**前向引用 `"BM25Index | None"` 能否在运行时正确求值**——这是本次改造唯一有风险的点。
用 `typing.get_type_hints()` 实测：求值为 `rag.bm25_retriever.BM25Index | None`，
正确。原理：`from __future__ import annotations` 让所有注解惰性求值，运行时根本不计算。

功能回归全过：切片仍 4 块且主题单一、BM25 三查询精确命中、RRF 融合与单路降级正常。

### 踩坑记录

- `typing.get_type_hints(模块)` **只返回模块级变量的注解**，不含函数注解。
  查函数要用 `typing.get_type_hints(函数对象)` 或 `函数.__annotations__`。
  我连续两次查错（`KeyError: 'retrieve'`）才发现，浪费时间。
- heredoc 在 Git Bash 下会被执行两次导致 patch 失效，写验证脚本应用 Write 工具落盘再执行。

# LangGraph 客服 Agent 工作流（agent/）

按用户给的规格实现 `state.py` / `nodes.py` / `graph.py`，DeepSeek 走 OpenAI 兼容接口
（`ChatOpenAI` + `base_url=https://api.deepseek.com/v1`）。

## 设计取舍

- **固定工作流而非自主 Agent**：客服问答是"检索 + 单次生成"，planner/reflection 循环
  只带来成本、延迟和不确定性。推理次数恒定：分类 1 次 + 生成 1 次（转人工路径仅 1 次）。
- **意图归一化表 `_INTENT_ALIASES`**：LLM 分类输出不稳定（中文/英文/带标点/带解释都出现过），
  必须归一化后才能当路由条件用。归一化失败一律落 `unknown` → 转人工，绝不猜。
- **四个节点都不抛异常**：异常会中断整张图。任何失败都降级为 `need_human=True`。
- **`generate_answer` 在上下文为空时不再调 LLM**：空上下文必然答不出，省一次无意义往返。

## 实测发现：DeepSeek 账户余额不足（402）

装完 `langchain-openai` 后用**真实接口**跑了一次，返回 `402 Insufficient Balance`。
链路没崩、按设计降级为转人工 —— 但日志只写"调用失败"，排查方向会完全跑偏（以为代码有 bug）。

于是加了 `_diagnose_llm_error()`：按 402/401/403/429 给出人话处置建议，附在每个 warning 后。
复跑确认输出：
```
意图分类调用失败，降级为 unknown: Error code: 402 - ... | 诊断: DeepSeek 账户余额不足，请到平台充值后再试（HTTP 402）
```
**经验**：降级设计得越平滑，越要在日志里区分"业务兜底"与"配置故障"——
否则用户看到"跑通了"，实际每次都在走兜底分支。

# 用户发来 bm25_retriever.py 截图 → 顺带全项目类型检查清零

## 截图与磁盘不一致（重要发现）

截图里是 `self._documents: list[str] = list[str](documents)`，但磁盘上的文件
（mtime 09:49，之后没被改过）是 `self._documents = list(documents)`。
全仓库 grep `list[str](` 无匹配，D 盘那份目录只有设计稿没有代码。
**结论：用户的编辑器是未保存缓冲区或过期视图，不是当前代码。**

## `list[str](documents)` 本身的技术结论（已实测）

- **合法**：`list[str]` 是 `types.GenericAlias`，调用时委托给 `list`，返回普通 list。
- **pyright 不报错**：对照实验两个变体都 0 诊断。
- **慢约 8 倍**：20 万次调用 0.20s vs 0.024s（每次都要构造 GenericAlias 再走 `__call__`）。
- **非惯用**：注解已写明 `list[str]`，构造处再写一遍泛型纯属冗余，可读性差。
- 推荐写法：`self._documents = list(documents)`（磁盘上已是）。

## 由截图引发的 pyright 全项目检查（真正有价值的部分）

装了 pyright 跑全项目，扫出 **8 个错误**，逐个修掉：

1. `agent/graph.py:97` — `config` 裸 dict 与 `RunnableConfig` 不兼容 → 显式标注
   `RunnableConfig`；invoke 返回值 `dict[str, Any] | Any`（LangGraph 桩粒度不够）
   → `cast(AgentState, ...)`。
2. `graph.py:139` — `total=False` 的 TypedDict 直接下标访问 pyright 无法证明键存在
   → 改 `.get("query", "")`。
3. `agent/nodes.py:93` — ChatOpenAI 的 `api_key` 类型签名要求 `SecretStr`
   → 包 `SecretStr(api_key)`。顺带正好符合"凭据不进 repr/日志"。
4. `api/main.py` 同样的 RunnableConfig + cast 问题 → 同法修。
5. `rag/loader.py:84,140` — `from langchain.text_splitter import ...` 兼容 shim
   被报缺包（langchain 1.x 已移除该模块，运行时验证确实 ModuleNotFoundError）。
   这是故意保留的兼容路径 → 加 `# pyright: ignore[reportMissingImports]` + 注释。

## Docker 构建失败排查：EOF 的两种根因（易混淆）

用户在 `pip install torch` 那一层构建失败：
`ERROR: failed to build: failed to receive status: rpc error: code = Unavailable desc = error reading from server: EOF`

### 排查路径（两次才找对）

1. 第一次归因"容器没有宿主机代理"——**部分正确但不完整**。实测确认：
   宿主机有 `http://127.0.0.1:62975` 代理、pip.ini 配了清华镜像，
   而容器两者都没有，torch 是唯一走境外源的大包（196MB）。这是真实的次因。
2. 改成宿主机预下载 wheel + 本地安装后，**仍然在同一层 EOF**。
   构建日志显示 `Processing /tmp/wheels/torch-...whl` 已命中本地、
   依赖从清华源全部 Collecting 成功，卡在 `Installing collected packages` 阶段。
   → 证明不是网络问题。
3. 跑 `docker info` 才拿到真根因：
   `Docker Desktop is unable to start / starting WSL engine ... exit status 0xc00000fd`
   `0xc00000fd` = STATUS_STACK_OVERFLOW，**WSL2 引擎崩了**，BuildKit 连接随之断开。
   且 Windows 侧 `D:/docker/desktop/resources/componentsVersion.json` 存在，
   WSL 内部 `/opt/docker-desktop/componentsVersion.json` 却缺失 → 发行版未初始化成功。

### 判据（写进 README 了）

`error reading from server: EOF` 只是表象。**看构建日志最后一行**：
- `Downloading torch-...` 卡住 → 网络问题，预下载 wheel 可解
- `Installing collected packages: ...` → 宿主环境 WSL 崩溃，与 Dockerfile 无关

### 另一个坑：pip download 比 curl 慢得多且会卡死

`pip download torch --index-url https://download.pytorch.org/whl/cpu --platform ... --python-version 3.11`
**6 分钟零字节落盘**。原因：pip 会顺带解析 torch 的依赖，而 filelock/sympy/jinja2 等
**不在 pytorch cpu 源上**，pip 对每个依赖反复重试直到超时。
改用 `curl` 直下 wheel（196MB / 47 秒），依赖交给国内镜像装，一步到位。
Dockerfile 里因此**不能用 `--no-index`**，要写 `pip install --find-links /tmp/wheels torch`，
让 torch 走本地 wheel、依赖走 PIP_INDEX_URL。

### Dockerfile 最终结构（已 `docker build --check` 通过）

ARG PIP_INDEX_URL（默认清华）/ ARG WITH_TORCH=1 / ARG TORCH_INDEX_URL，
写 `/etc/pip.conf` 带 retries=10 timeout=120；wheels/ 有 .whl 走本地、没有走联网；
WITH_TORCH=0 时用 `grep -v '^torch$'` 剔除 torch，否则会被 sentence-transformers
的间接依赖重新拉回（还可能是 CUDA 版）。
